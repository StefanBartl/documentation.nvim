# Interface languages (i18n) — cost analysis and task breakdown

**Not the same axis as [`MULTILANG.md`](MULTILANG.md).** That document is
about the languages this tool *reads* — Lua, JS/TS, Python. This one is about
the language it *speaks*: the tab labels, the drift findings, the health
report, the desktop app's buttons. The two share a word and almost nothing
else, with exactly one real intersection, recorded in Part 5.

Nothing here is built. Written 2026-08-18.

---

## Part 1 — the three surfaces, and where the cost actually is

The intuition is that a Neovim plugin's messages are the expensive part. They
are not; they are the cheapest thing in the tree by an order of magnitude.

| Surface | Where | Measured size | Share of the work |
|---|---|---:|---|
| **The generated page** | `core/render/html.lua` | 7 433 lines, English inline in JS string concatenation | **~85 %** |
| ~~Drift findings~~ **done** | `core/check.lua` — **24** checks (16 when this was written) | **10** rendering edges, one catalog | small code, largest consequence (Part 2.1) |
| Editor messages | `vim.notify` / health, across `lua/` | **14 call sites total** | trivial |
| CLI / engine report | `standalone/docmap.lua`, `core/cli.lua` | one report shape | small |
| Markdown / PDF | `core/render/markdown.lua` | headings and table captions | small |
| Desktop app | `docmap-desktop` `src/index.html`, `src/main.js`, Rust `Err(...)` strings | 119 + 650 lines + ~30 error strings | small |

So: this is one large job (the page) and five small ones. Plan it that way
rather than treating "translate the plugin" as one uniform effort — the page
alone will outweigh everything else combined, and it is also the surface most
people actually read, including people who never open Neovim.

## Part 2 — four rules, decided before any string is extracted

Each of these is cheap to honour now and expensive to retrofit.

### 2.1 The IR never contains translated text

`docs/map/module_map.json` is byte-deterministic and `--check` compares it.
A finding whose `message` field is a pre-formatted English sentence — which
is what `check.lua`'s `add()` produces today — becomes locale-dependent the
moment it is translated, and CI's verdict would then depend on the machine's
`LANG`. That is not a translation bug, it is a correctness bug in the drift
check.

The fix is to stop formatting at the point of detection:

```lua
-- today
add(list, "warn", "undocumented-param", node.id,
    ("%s: parameter %s is not documented"):format(fn.name, p))

-- structured
add(list, "warn", "undocumented-param", node.id,
    { fn = fn.name, param = p })
```

…and format at each edge instead (quickfix, page, report, MCP response). The
IR then carries a check id and its parameters, both locale-free and both
already deterministic.

**Worth doing even if i18n is never built.** A structured finding is
machine-readable, which is what `core/mcp/tools.lua` and `--api` want from
findings anyway, and what would let a host group or filter them without
parsing English prose back out.

### 2.2 One artifact, every language

The page is self-contained by design — no CDN, no build step. The temptation
is one page per locale (`index.de.html`); resist it. Catalogs are kilobytes
against a 1.5 MB artifact, so bundle all of them and switch at runtime:
`navigator.language` picks the default, a control in the page header
overrides it, the choice persists the same way marks and hidden nodes already
do via the URL. <https://stefanbartl.github.io/documentation.nvim/> stays one
URL, and a link someone shares keeps working regardless of which language
either party reads.

### 2.3 Untranslated is visible, never invisible

A missing key falls back to the English source string — never to a blank,
never to the raw key. A debug mode (`?i18n=debug`, mirroring the existing
`DOCMAP_TS_DEBUG` posture) marks fallbacks visibly so a half-finished locale
is measurable rather than merely embarrassing. This repository's own standing
position is that silent degradation is the most expensive failure mode; a
locale at 60 % that looks finished is exactly that failure.

### 2.4 The interface is translated; the subject never is

Module names, `@module` paths, file paths, identifiers, docstring prose, git
author names and commit subjects are the user's content. They stay verbatim
in every locale. The catalog namespace covers chrome only, and the boundary
should be visible in code — a helper that takes a user string and a helper
that takes a key are two different functions, not one with a flag.

Corollary for the language picker itself: locale names are shown as endonyms
(`Deutsch`, `日本語`, `العربية`), never translated into the current UI
language.

## Part 3 — which languages, and what each one actually costs

"As many as possible" is the goal; "not sloppily" is the constraint, and the
two only coexist if shipping a locale has a bar. The bar:

| Tier | Meaning |
|---|---|
| **Source** | `en`. Every string is written here first; every other catalog is a translation of it. |
| **Maintained** | Has someone who reads the language and reviews changes. Ships in the picker unmarked. `de` is the only one that qualifies today (author is a native speaker). |
| **Contributed** | Arrived with a maintainer. Same status as maintained; no pre-commitment to any specific language. |
| **Machine-assisted** | Generated, unreviewed. Ships **only** behind an opt-in and **says so in the UI**. A wrong translation that looks authoritative is the 2.3 failure again, one level up. |

### The per-language work that is not "a catalog"

This is the part that makes a locale real rather than a file of strings.

| Locale | What it needs beyond translated strings |
|---|---|
| **de** | Compound nouns are long (`Abhängigkeitsgraph`, `Modulzugehörigkeit`) — the sidebar, the tab bar and the button row are all sized against English. Layout pressure, not vocabulary, is the actual work. Phrase in imperatives so the du/Sie question never has to be answered. |
| **fr, es, it, pt-BR** | +20–30 % string length against English; same layout pressure as `de` for a different reason. French needs a narrow no-break space before `: ; ! ?` — a plain space is a typographic error, and a normal no-break space is the wrong width. |
| **ru, uk, pl, cs** | CLDR plural categories `one/few/many/other`. This is where a `n == 1 ? a : b` helper stops being a shortcut and starts being wrong — `2 модуля` vs `5 модулей`. The plural machinery has to be real before any of these ships. Cyrillic font stack in the page. |
| **ja, zh-Hans, zh-Hant, ko** | The opposite problem: exactly one plural category. No word spaces, so tree labels and graph node text need `line-break: strict` / `overflow-wrap: anywhere` rather than the Latin word-wrap the page assumes. Font stack must not fall through to a Latin-only face. **Italic is wrong for CJK** — the page uses it for module summaries, and that has to become a non-italic emphasis in these locales. |
| **ar, he, fa** | RTL, and the one genuinely interesting decision in this document — see below. Requires logical CSS properties (`margin-inline-start`, `padding-inline-end`) throughout, which is a mechanical but repo-wide edit to `html.lua`'s inline CSS. Arabic-Indic vs. ASCII digits is a per-locale choice, not automatic. |
| **tr** | Dotted/dotless `i`. Any case transform applied to a translated string is a bug (`I`.lower() is `ı`, not `i`) — so: **no `text-transform` on catalog output, anywhere**, and no `:lower()`/`:upper()` on it in Lua. The page currently uses uppercase styling on at least the tab labels; that has to become part of the catalog, not a CSS effect. |
| **hi, th, vi** | Tall glyph stacks clip in line heights tuned against Latin metrics. Line-height becomes a per-script value, not a constant. |

### RTL and the graphs — the decision worth making once

The Hierarchy tab draws six directed graphs. An arrow there means *requires*,
*calls*, *inherits from*. Mirroring the canvas the way `dir="rtl"` mirrors a
paragraph would reverse the arrows' apparent direction and change what the
picture claims.

So the rule is: **chrome mirrors, content flow does not.** The sidebar, tab
bar, panels and prose flip. The graph canvas keeps its left-to-right layout,
with the labels *inside* the nodes rendered RTL. Code snippets stay LTR in
every locale, for the same reason — code is not prose in any language. This
mirrors the position `MULTILANG.md` already takes about not inventing
structure that is not there: a diagram means what it means regardless of the
reading direction of the surrounding text.

### Cross-cutting formatting

- **Numbers.** The page can use `Intl.NumberFormat`. The Lua side (report,
  markdown, quickfix) has no ICU and will not grow one — it stays ungrouped
  ASCII digits everywhere. State that as a decision rather than let the two
  halves drift into disagreeing about `1234` vs `1 234`.
- **Dates.** The History tab shows commit dates → `Intl.DateTimeFormat`. Git
  author names and commit subjects are 2.4 content and stay verbatim.
- **Plurals.** CLDR categories on both hosts. The page can lean on
  `Intl.PluralRules`; the Lua side needs a small hand-written CLDR subset —
  one function per category set, not one per language.
- **Sorting.** The Index tab sorts names. `Intl.Collator` with the active
  locale, or `de` puts `ä` after `z` and `sv` puts it correctly at the end
  *on purpose* — the same character, two right answers, which is exactly why
  this cannot be a hardcoded comparator.

## Part 4 — task breakdown

### I18N-0 — structured findings — **built 2026-08-20**

- [x] `check.lua`'s `add()` takes `(severity, check, node_id, params)`; all
      **24** call sites — the count was 16 when this was written — pass a
      table instead of a formatted string.
- [x] One formatter module, `core/findings.lua`, called at each of the
      **ten** edges: quickfix, diagnostics, CLI report, page, markdown,
      mdview, SARIF, MCP, and the specs.
- [x] `module_map.json` gains the params and loses the prose. Schema 5.
- [x] **Acceptance met**, three ways: 140 rendered findings across three
      real repositories byte-compared before and after; the twenty-one
      specs that assert exact finding text unchanged in what they assert;
      and `findings_spec.lua` covering the two checks neither reaches.

**Two corrections this task owes to whoever reads it next**, both found by
measuring rather than by reading:

1. **Findings were never in `module_map.json`.** The third item above was
   written on the assumption that they were. `init.lua` serialises an
   explicit whitelist and has never included them — so *that* half of the
   acceptance criterion was already true, and the schema bump was owed to
   something else entirely.
2. **The English in the artifact is almost all subject, not interface.**
   Counted over this repository's own `module_map.json`: **820** sentences
   are node summaries and **118** more are the repository's own docs and
   features — all of which rule 2.4 says must *never* be translated.
   Exactly **10** were the tool speaking English about the tree, and all ten
   were `quicks`' `headline`/`basis`/`detail`. Those now ride on the page,
   which builds its own payload, exactly as `glossaries` and `marker_kinds`
   already do; the artifact carries `value`/`n`/`total` instead, so "45 of
   72" survives in a form any language can phrase.

So "no English sentence in `module_map.json`" is **not** the right goal and
should not be restated as one: it would require translating module
summaries, which rule 2.4 forbids. The goal it stood in for — no *interface*
English in the artifact — is met.

**Named placeholders, not positional ones.** `{from} requires {to}` rather
than `%s requires %s`: four anonymous slots cannot be reordered by a
translator, and German, Japanese and Arabic each need a different order.
This is the decision the rest of the catalog work inherits.

**One defect the byte comparison could not catch**, kept because it
generalises: the first formatter escaped `%` in substituted values, which
`gsub` only needs for a replacement *string* and never for what a
replacement *function* returns — so a `%s` inside an `@example` parse error
came out as `%%s`. Three real repositories produced no finding containing a
percent sign, so only the dedicated spec found it. A corpus that happens not
to contain a case is not evidence the case works.

### I18N-1 — catalog infrastructure and `en` extraction

- [ ] Catalog format: flat key → string, one file per locale, plural forms as
      a category table. JSON, so both hosts read it with what they already
      have (`core/json.lua`; `JSON.parse`).
- [ ] Two runtimes, one format: a Lua `t(key, params)` and a JS `t(key,
      params)` with identical semantics including the 2.3 fallback.
- [ ] Locale resolution: `v:lang`/`$LANG` in the editor, `navigator.language`
      in the page, the OS locale in the desktop app, each overridable —
      `opts.locale`, a page control, an app setting.
- [ ] Extraction of the English source catalog is **manual and reviewed**,
      not a regex sweep. `html.lua` builds strings by concatenation; a sweep
      would split sentences at interpolation boundaries and produce keys that
      cannot be translated as sentences. That failure is not recoverable
      later without redoing the work.
- [ ] **Acceptance:** `en` runs entirely through the catalog on every surface,
      output unchanged.

### I18N-2 — editor half and CLI report

The 14 `vim.notify` sites, health, and the engine's report. Small enough to
land in one pass, and it proves the Lua runtime before the page depends on it.

### I18N-3 — the generated page

The large one. Split by panel so it is reviewable, not one 7 433-line commit:

- [ ] Chrome: header, tab bar, controls, empty states.
- [ ] Quicks / Tree / Index / Notes panels.
- [ ] Hierarchy: the six graph views' controls and legends (labels only —
      layout stays as-is until I18N-7).
- [ ] Analysis: the eight ranking panels, including their explanatory prose.
- [ ] History / Telemetry / Loaded / Compare / Features, including the
      "computed on demand, this host cannot answer it" messages — the most
      carefully worded strings in the tree, and the ones a bad translation
      damages most.
- [ ] Findings rendering switches to I18N-0's formatter.

### I18N-4 — the desktop app

`docmap-desktop`: `src/index.html`, `src/main.js`, and the Rust `Err(String)`
messages. The Rust half is the one to watch — those strings cross the IPC
boundary as data and are shown verbatim, so they need the same key-plus-params
treatment as I18N-0's findings, not a translated string baked in Rust.
Tracked on that side in `docmap-desktop/docs/ROADMAP.md`.

### I18N-5 — `de`, the first real second locale

Not a formality: it is the test of every rule in Part 2 and the layout
pressure in Part 3 at once. Nothing after this phase starts until the German
page has been looked at in a real window — see `docs/HANDOVER.md` on the two
already-built things still awaiting visual review, which is the same debt.

### I18N-6 — plural and format machinery, proven by a locale that needs it

`ru` or `pl`. Until a `few`/`many` locale exists, the plural code is untested
by construction.

### I18N-7 — RTL (`ar`)

Logical CSS properties throughout `html.lua`, plus the chrome-mirrors-content-
does-not rule from Part 3 implemented and *looked at*.

### I18N-8 — CJK (`ja`)

Line breaking, font stack, the italic substitution.

### I18N-9 — the contribution path

- [ ] Documented process for adding a locale, with the tier bar from Part 3.
- [ ] CI gate: a shipped locale below its completeness threshold fails, rather
      than degrading quietly to English in production.
- [ ] The machine-assisted marker in the UI, if that tier is ever used.

## Part 5 — the one intersection with `MULTILANG.md`

Both plans rewrite `check.lua`'s `add()`:

- `MULTILANG.md` Part 4's **C.6** makes each check declare which doc
  convention it needs, so a check with nothing to compare against reports
  "not applicable" rather than passing silently.
- **I18N-0** above makes each check emit parameters instead of a sentence.

Same function, same call sites, same checks — 24 of them now, 16 when this
was written. The advice was to do them in one pass so the second would not
rewrite the first.

**That did not happen, and the cost is small but real.** I18N-0 shipped
2026-08-20 without applicability, so a finding is `{ check, node, params }`
and the C.6 work will add a fourth field and touch all 24 call sites a
second time. The reason it went first is worth recording: I18N-0 blocks
every other I18N task and applicability was not scheduled, so waiting for it
would have blocked the axis that *was* being worked on. Adding one field to
a table is also a much smaller second pass than the rewrite this paragraph
was warning about, which was two competing shapes for the same argument.

Note also that MULTILANG.md has no section literally labelled **C.6** — the
applicability idea appears there as prose. Anything scheduling this work
should quote it rather than the label.
